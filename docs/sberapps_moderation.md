## Что уже подготовлено

- Backend принимает запросы SmartApp API на `POST /api/v1/sber/webhook`.
- `CLOSE_APP` возвращает `204`, потому что ассистент не ожидает ответ на закрытие.
- Ответы `ANSWER_TO_USER` содержат `pronounceText`, `items`, `suggestions`, `auto_listening`, `finished` и не содержат `null`.
- Тексты ответов приводятся к одной строке без переносов.
- Пошаговые сценарии включают `auto_listening`, когда от пользователя нужен следующий ответ.
- `Помощь`, неизвестная команда и ошибки распознавания не оставляют пользователя в тупике.
- Справка о препаратах только информационная, с дисклеймером.
- Локальный справочник содержит 30 препаратов с краткой справкой и противопоказаниями.
- Локальный каталог аптек содержит mock-цены по всем препаратам из справочника.
- Персональные медицинские рекомендации блокируются безопасным отказом.
- Видимые демо-данные не используют бренды Сбера, Салюта или имена ассистентов.
- Стартовый Canvas-интерфейс открывается пустым мастером настройки без предустановленных препаратов.
- Есть статический frontend в `frontend/` и архив `grannycare-frontend.zip`.
- Добавлены e2e/moderation tests: запуск, помощь, добавление лекарства, поиск аптек, безопасный отказ, режим без экрана, `SERVER_ACTION`, выход.

## Что важно перед отправкой

### Backend

В Studio для сценария SmartApp API нужна внешняя HTTPS-ссылка на backend:

```text
https://<ваш-домен>/api/v1/sber/webhook
```

Проверьте перед отправкой:

- HTTPS включен, TLS не ниже 1.2.
- `/health` отвечает `{"status":"ok"}`.
- Средний ответ webhook держится около 1 секунды, максимум не выходит за 1,5 секунды.
- При ошибках сервис возвращает управляемый ответ, а не traceback.
- Логи не содержат лишних персональных данных и медицинских сведений.
- `data/runtime_state.json` не коммитится и не используется как постоянное production-хранилище с реальными пользователями.

Для production лучше заменить JSON-хранилище на БД с резервным копированием и контролем доступа.

### Docker Compose на сервере

В проект добавлены [Dockerfile](../Dockerfile) и [docker-compose.yml](../docker-compose.yml). Compose поднимает backend на `127.0.0.1:8000`, хранит runtime-состояние в volume `grannycare-state` и не кладет `data/runtime_state.json` в образ.

Запуск на сервере:

```bash
git clone <ваш-репозиторий>
cd <папка-проекта>
docker compose up -d --build
docker compose ps
curl http://127.0.0.1:8000/health
```

Если порт `8000` занят, задайте другой локальный порт:

```bash
BACKEND_PORT=8001 docker compose up -d --build
curl http://127.0.0.1:8001/health
```

Для Studio по-прежнему нужна внешняя HTTPS-ссылка. На сервере оставьте compose-порт локальным и прокиньте домен через Nginx/Caddy/другой reverse proxy на `http://127.0.0.1:8000`:

```text
https://<ваш-домен>/api/v1/sber/webhook -> http://127.0.0.1:8000/api/v1/sber/webhook
```

После обновления кода:

```bash
git pull
docker compose up -d --build
docker compose logs -f backend
```

### Привязка домена и HTTPS

Самый простой production-вариант для этого проекта: домен смотрит на сервер, а Caddy в Docker автоматически получает и обновляет HTTPS-сертификат Let's Encrypt.

1. На стороне регистратора домена добавьте DNS-запись:

```text
A    <ваш-домен>    <публичный IPv4 сервера>
```

Если используете поддомен, например `api.example.com`, добавьте запись именно для него:

```text
A    api    <публичный IPv4 сервера>
```

2. На сервере откройте входящие порты `80` и `443`. Они нужны Caddy для выпуска сертификата и HTTPS-трафика.

3. Создайте `.env` из шаблона и укажите ваш домен:

```bash
cp .env.example .env
nano .env
```

Пример:

```env
DOMAIN=api.example.com
ACME_EMAIL=admin@example.com
BACKEND_PORT=8000
```

Для кириллического домена `сберапп.рф` безопаснее указать punycode-вариант:

```env
DOMAIN=xn--80abm5bade.xn--p1ai
ACME_EMAIL=admin@example.com
BACKEND_PORT=8000
```

В браузере и Studio после этого можно использовать обычную кириллическую ссылку:

```text
https://сберапп.рф/api/v1/sber/webhook
```

4. Поднимите backend вместе с HTTPS-прокси:

```bash
docker compose -f docker-compose.yml -f docker-compose.https.yml up -d --build
docker compose -f docker-compose.yml -f docker-compose.https.yml ps
docker compose -f docker-compose.yml -f docker-compose.https.yml logs -f caddy
```

5. Проверьте снаружи:

```bash
curl https://api.example.com/health
```

Ожидаемый ответ:

```json
{"status":"ok"}
```

Webhook для Studio:

```text
https://api.example.com/api/v1/sber/webhook
```

Если на сервере уже есть Nginx/Caddy, который занимает `80` и `443`, не запускайте `docker-compose.https.yml`. В этом случае оставьте текущий backend на `127.0.0.1:8000` и добавьте reverse proxy в существующий веб-сервер.

Если браузер пишет, что соединение неожиданно прервано, проверьте на сервере:

```bash
docker compose -f docker-compose.yml -f docker-compose.https.yml ps
docker compose -f docker-compose.yml -f docker-compose.https.yml logs --tail 100 caddy
docker compose -f docker-compose.yml -f docker-compose.https.yml logs --tail 100 backend
curl http://127.0.0.1:8000/health
curl -vk https://сберапп.рф/health
sudo ss -ltnp | grep -E ':80|:443|:8000'
```

Рабочий backend через HTTPS должен отвечать на `/health`. Сам `/api/v1/sber/webhook` открывается методом `POST`; при обычном открытии в браузере `GET` может вернуть `405 Method Not Allowed`, и это нормально. Ошибка TLS или `Empty reply from server` означает, что проблема в HTTPS-прокси, firewall или в том, что порты `80/443` заняты другим сервисом.

### Персональные данные

Проект хранит `user_id`, список лекарств, расписание приема и опционально контакт родственника. Это может считаться персональными данными, а часть информации относится к чувствительной медицинской тематике.

Перед публикацией подготовьте политику конфиденциальности. В ней нужно раскрыть:

- кто является оператором данных;
- какие данные собираются;
- зачем они нужны;
- срок хранения;
- кто имеет доступ;
- передаются ли данные третьим лицам или за пределы РФ;
- как пользователь может запросить удаление или изменение данных;
- контакты владельца приложения.

Если публикация идет от юридического лица и нужны персональные данные пользователей, дополнительно свяжитесь с поддержкой Sber Developers по адресу `developer@sberdevices.ru`.

Черновой шаблон для заполнения лежит в [privacy_policy_template.md](privacy_policy_template.md).

### Контент и медицинская безопасность

Не добавляйте в сценарии:

- диагнозы;
- назначение лечения;
- персональные рекомендации вида "что мне принимать";
- обещания эффективности;
- рекламу аптек или лекарств;
- внешние ссылки на покупку без HTTPS и явного назначения перехода.

Допустимая формулировка для справки:

```text
По инструкции препарат используется для ...
Информация носит справочный характер и не заменяет консультацию врача.
```

### Карточка каталога

Рекомендуемое название:

```text
Помощник здоровья
```

Почему так: название отражает основную функцию приложения, не использует бренд Сбера и укладывается в лимит 50 символов.

Короткое название:

```text
Помощник здоровья
```

Активационные имена, до 5:

```text
Помощник здоровья
Помощник по здоровью
Здоровье помощник
Лекарственный помощник
Помощник лекарств
```

Короткое описание, 20-84 символа:

```text
Напоминания о лекарствах и справка по инструкции
```

Описание:

```text
Помощник здоровья помогает вести расписание приема лекарств, напоминать о приеме, подтверждать или откладывать напоминания, смотреть день курса и получать справочную информацию по инструкции к препарату. Приложение не ставит диагнозы, не назначает лечение и не заменяет консультацию врача.
```

Категории: выберите до двух максимально близких к приложению. Если в Studio есть категория про здоровье или полезные сервисы, используйте ее. Не выбирайте игровые или развлекательные категории.

Возрастное ограничение: не ставьте `0+`. Из-за тематики лекарств обычно безопаснее выбрать не ниже `12+`; финальное значение сверяйте с доступными вариантами Studio и вашим юридическим описанием.

Примеры запуска, максимум 4:

```text
Запусти Помощник здоровья
Открой Помощник здоровья
Включи Помощник здоровья
Запусти Помощник по здоровью
```

## Частые вопросы и возможные ошибки

Скопируйте этот блок в поле `Частые вопросы и возможные ошибки`.

```text
1. Приложение не назначает лечение и не заменяет врача.
2. Справка о препаратах берется из локального демонстрационного справочника.
3. Поиск аптек работает на локальном демонстрационном каталоге и не оформляет покупку.
4. Фразы времени "каждый день в 9 утра" и "в 9 утра" поддерживаются в пошаговом сценарии добавления лекарства.
5. Если лекарство не найдено в расписании, добавьте его командой "Добавь лекарство".
6. Экранные кнопки Canvas-интерфейса отправляют команды ассистенту, а расписание обновляется через smart_app_data.
7. В текущей версии нет платежей, монетизации, внешних ссылок и медицинских консультаций.
```

Если перед реальной публикацией подключите настоящий аптечный API, замените пункты про демонстрационные данные и отдельно проверьте достоверность цен, наличие товара и правила внешних ссылок.

## Если модерация отклонила сценарий

Формулировка "не отработал указанный сценарий" обычно означает, что модератор смог открыть карточку смартапа, но один из голосовых шагов не получил ожидаемый ответ от SmartApp API.

Перед повторной отправкой проверьте:

- В поле `Внешняя ссылка` указан webhook сценария, а не healthcheck: `https://сберапп.рф/api/v1/sber/webhook`.
- Если Studio принимает только домен без пути, backend также принимает `POST /` и обрабатывает его как SmartApp webhook.
- Проверка идет именно POST-запросом. `GET /health` подтверждает только, что сервер жив, но не проверяет голосовой сценарий.
- На сервер выкачана последняя версия backend. В ней `payload.intent`, который Studio возвращает из предыдущего ответа, не ломает пошаговый сценарий добавления лекарства.
- После деплоя выполнен тест запуска и хотя бы первый пошаговый сценарий: `Запусти Помощник здоровья` -> `Добавь лекарство` -> `Аспирин` -> `Каждый день в 9 утра` -> `7 дней`.

## Алгоритм повторной отправки после замечаний


3. Убедитесь, что результат соответствует текущей версии:

```text

```

4. Пересоберите архив frontend:

```powershell
Compress-Archive -Path frontend\* -DestinationPath grannycare-frontend.zip -Force
```

5. Загрузите новый `grannycare-frontend.zip` в поле `Хостинг фронтенда` в Studio.
6. Задеплойте backend на сервер и перезапустите контейнеры:

```bash
git pull
docker compose up -d --build
```

7. Проверьте, что backend жив:

```powershell
Invoke-RestMethod https://сберапп.рф/health
```

8. Проверьте SmartApp webhook POST-запросом, а не открытием ссылки в браузере:

```powershell
Invoke-RestMethod https://сберапп.рф/api/v1/sber/webhook `
  -Method Post `
  -ContentType "application/json" `
  -Body '{"sessionId":"check-session","messageId":1,"messageName":"RUN_APP","uuid":{"userChannel":"B2C","sub":"check-user","userId":"check-user"},"payload":{"new_session":true,"meta":{"features":{"screen":{"enabled":true}}},"device":{"surface":"SBERBOX","capabilities":{"screen":{"available":true},"speak":{"available":true}}}}}'
```

9. В ответе проверьте, что текст содержит `Расписание пока пустое`, а не список готовых препаратов.
10. В Studio откройте раздел тестирования смартапа и пройдите сценарий текстом:

```text
Добавь лекарство
Аспирин
Каждый день в 9 утра
7 дней
```

11. Повторите тот же сценарий, но на шаге времени скажите:

```text
В 9 утра
```

12. Если оба варианта приводят к вопросу о курсе и потом добавляют лекарство на `09:00`, отправляйте смартап на повторную модерацию.

## Алгоритм проверки голосового ввода без колонки

1. Откройте Studio и перейдите в карточку смартапа.
2. Выберите версию `Черновик`.
3. Откройте раздел `Тестирование`.
4. В эмуляторе сначала проверьте сценарий текстовым вводом. Это отсечет ошибки backend и сценария.
5. Переключитесь на голосовой ввод в эмуляторе.
6. Разрешите браузеру доступ к микрофону.
7. Произнесите по очереди:

```text
Добавь лекарство
Аспирин
Каждый день в 9 утра
7 дней
```

8. Затем начните новый тестовый проход и на шаге времени произнесите:

```text
В 9 утра
```

9. В логах эмулятора посмотрите, какой текст пришел в SmartApp API. Если там есть `Каждый день в 9 утра` или `В 9 утра`, backend должен распознать время как `09:00`.
10. Если хотите прогнать заранее записанный голосовой файл, используйте виртуальный микрофон на компьютере и подайте аудио в браузерный эмулятор. Напрямую в webhook аудиофайл отправить нельзя: SmartApp API передает backend уже распознанный текст.
11. Для отдельной проверки распознавания аудиофайла можно использовать SaluteSpeech API или приложение SaluteSpeech, но это проверит только speech-to-text. Полный сценарий смартапа все равно нужно проверять через Studio, приложение Салют или устройство.

## Куда вставлять SDK key

SDK key из Studio не вставляется в поле `Внешняя ссылка`, не отправляется в webhook и не нужен для обычной проверки POST-запросом через PowerShell.

Этот ключ нужен только для локального браузерного теста через Assistant Client. По документации его получают в Studio: `Настройки` -> `Настройки сервисов` -> `SmartApp` -> `Эмулятор`. Ключ действует 24 часа; если вы случайно раскрыли его в переписке или он истек, нажмите `Обновить ключ` и используйте новый.

Практический выбор:

1. Если проверяете backend и модерационный сценарий, SDK key не нужен. Используйте POST-запросы к `https://сберапп.рф/api/v1/sber/webhook` и тест в Studio/приложении Салют.
2. Если проверяете Canvas в браузере через Assistant Client, SDK key передается в код отладчика, обычно в параметр `token`/`getState`, в зависимости от используемого шаблона Assistant Client.
3. Если у вас нет отдельной страницы с Assistant Client, не вставляйте ключ никуда. Для текущей задачи достаточно проверить webhook, загрузить новый frontend-архив и пройти сценарий в тестировании смартапа.

## Локальное тестирование

Установка:

```powershell
python -m venv .venv
.\.venv\Scripts\activate
pip install -r requirements.txt
```

Полный тестовый прогон:

```powershell
pytest -q
```

Ожидаемый результат на текущей версии:

```text
24 passed
```

Локальный запуск backend:

```powershell
uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Проверка healthcheck:

```powershell
Invoke-RestMethod http://127.0.0.1:8000/health
```

Проверка SmartApp webhook:

```powershell
Invoke-RestMethod http://127.0.0.1:8000/api/v1/sber/webhook `
  -Method Post `
  -ContentType "application/json" `
  -Body '{"sessionId":"demo-session","messageId":1,"messageName":"RUN_APP","uuid":{"userChannel":"B2C","sub":"demo-user","userId":"demo-user"},"payload":{"new_session":true,"meta":{"features":{"screen":{"enabled":true}}},"device":{"surface":"SBERBOX","capabilities":{"screen":{"available":true},"speak":{"available":true}}}}}'
```

Проверка через Docker Compose:

```powershell
docker compose up -d --build
Invoke-RestMethod http://127.0.0.1:8000/health
Invoke-RestMethod http://127.0.0.1:8000/api/v1/sber/webhook `
  -Method Post `
  -ContentType "application/json" `
  -Body '{"sessionId":"docker-session","messageId":1,"messageName":"RUN_APP","uuid":{"userChannel":"B2C","sub":"docker-user","userId":"docker-user"},"payload":{"new_session":true,"meta":{"features":{"screen":{"enabled":true}}},"device":{"surface":"SBERBOX","capabilities":{"screen":{"available":true},"speak":{"available":true}}}}}'
docker compose down
```

## Последний чек перед отправкой

- `pytest -q` проходит.
- `docker compose up -d --build` поднимает backend, `/health` отвечает `{"status":"ok"}`.
- `grannycare-frontend.zip` пересобран после последних изменений.
- Backend доступен извне по HTTPS.
- В Studio заполнены название, сценарий, хостинг frontend, описание, категории, примеры запуска, инструкции тестирования и FAQ.
- Загружены иконки и превью нужного размера.
- Есть политика конфиденциальности.
- В приложении нет платежей, рекламы, чужих брендов и логотипов.
- Модератор сможет пройти все сценарии из инструкции без тестовых аккаунтов и ручных действий вне Studio.
- Если приложение публикуется от юридического лица или ИП, подготовлены документы для публикации.

После модерации публикация в каталоге становится доступна в Studio. По документации проверка проводится вручную в рабочие дни и может занимать до трех рабочих дней.
